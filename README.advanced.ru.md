## 1. Назначение и правила чтения

Это руководство описывает архитектуру и рабочую модель ASB. Оно намеренно не является историей релизов: технические подробности включены сюда тогда, когда помогают безопасно настраивать, тестировать, диагностировать или проверять модуль.

Короткий [README.ru.md](README.ru.md) остаётся обычной точкой входа. Здесь предполагается, что читатель понимает root-модули, системные свойства Android, sysfs, базовые команды shell и разницу между запрошенным и наблюдаемым значением.

| Термин | Значение в этом руководстве |
|:---|:---|
| **Запрошено / requested** | Значение, которое профиль, пользовательская настройка или нативный governor попросил использовать систему. |
| **Фактическое / effective, observed** | Значение, которое соответствующий интерфейс показывает после запроса. Один успешный системный вызов записи ещё ничего не доказывает. |
| **Принадлежит ASB / owned** | Параметр, для которого у ASB есть определённый writer, исходное значение и путь восстановления. |
| **Ограничено vendor** | Прошивка, PowerHAL, thermal-движок или другой владелец платформы сейчас удерживает другое значение. |
| **Not exposed** | Ожидаемое доказательство или интерфейс недоступны через пути, которые ASB может прочитать. Это не доказывает отсутствие аппаратной возможности. |
| **Unknown** | Надёжных данных для утверждения недостаточно. Неизвестное состояние является полноценным результатом диагностики. |
| **Not runtime-discoverable** | Возможность нельзя надёжно установить через текущие runtime-интерфейсы. Недостающее значение нельзя заменять догадкой. |
| **Baseline** | Значение до вмешательства ASB, сохранённое для восстановления принадлежащего модулю параметра. |

> **Центральное правило:** отсутствие read-only доказательства не является доказательством отсутствия. ASB не должен превращать нечитаемый интерфейс в уверенное заявление «не поддерживается», «активно» или «сток».

## 2. Принципы проектирования

ASB объединяет нативный governor производительности, shell-applier'ы, WebUI, дополнительные аудиокомпоненты и диагностику по запросу. Эти части используют общие настройки и доказательства, но не становятся взаимозаменяемыми владельцами одного параметра.

| Принцип | Практическое следствие |
|:---|:---|
| 🧭 **Один определённый владелец policy-пути** | Shell и native-код не ведут постоянную борьбу за один узел. Владение и передача управления заданы явно. |
| 🌡 **Термозащита платформы важнее тюнинга** | ASB не отключает vendor thermal protection ради результата бенчмарка. Более строгое ограничение платформы может победить. |
| 🔍 **Возможности определяются устройством** | Границы частот и открытые интерфейсы обнаруживаются на текущем устройстве, а не копируются с чужого SoC. |
| 🧪 **Доказательство раньше успеха** | Диагностика различает выбранное, записанное, наблюдаемое, отклонённое, недоступное и неизвестное состояния. |
| 🧠 **Ограниченное обучение** | Smart использует проверенные окна и барьеры; подсказка из лога не становится вторым writer настроек. |
| 🔋 **Профили остаются разными** | У Battery есть собственная политика экономии. Он незаметно не превращается в Smart, а Performance не является универсальным набором частот в кГц. |
| 🕵 **Подробный сбор по запросу** | Расширенные записи запускает пользователь. Инвентарь устройства read-only и не получает постоянный polling-collector. |
| 🔐 **Минимум данных** | Серийные номера, IMEI, аккаунты и сетевые идентификаторы не нужны диагностике и не собираются для отчётов. |
| ↩️ **Обратимость** | Baseline, записи применения и восстановление являются частью функции, а не дополнением на потом. |
| 📦 **Patch-based поставка модуля** | Модуль патчит или перекрывает доступное поведение механизмами root-модуля; для этих политик не требуется встраивать произвольные APK. |

## 3. Общая архитектура

| Уровень | Основная ответственность | Характерные исходники |
|:---|:---|:---|
| **Жизненный цикл модуля** | Установка, порядок загрузки, передача состояния при обновлении, возврат stock и удаление. | `customize.sh`, `common/install.sh`, `post-fs-data.sh`, `service.sh`, `uninstall.sh` |
| **Политика профилей** | Выбор профиля, генерация диапазонов, ручные applier'ы и передача управления Stock. | `apply_profile.sh`, `profiles/`, `runtime/profile_core.sh`, `runtime/asb_stock_policy.sh` |
| **Device-adaptive bounds** | Read-only обнаружение, идентичность топологии, OPP-aware синтез и отклонение устаревших данных. | `tools/asb_discover.sh`, `tools/asb_synthesize_bounds.sh`, `runtime/asb_device_bounds.sh` |
| **Нативный governor** | Сбор метрик, выбор состояния, реакция на температуру, оценка Smart и принадлежащие ему записи. | `src/asb_governor.c`, `src/asb_fsm.h`, `src/asb_writer.h`, `src/asb_smart.h` |
| **Runtime feature appliers** | Звук, сеть, Doze, интерфейс, камера, фоновая работа и vendor-настройки. | `runtime/asb_*.sh` |
| **WebUI и Action** | Настройки, live-monitor, именованные конфигурации, сведения об устройстве, отчёты и результат применения. | `webroot/index.html`, `action.sh`, `webroot/config.json` |
| **Audio DSP** | Дополнительная цепочка обработки, выбор маршрута, live-параметры и интеграция audio effect. | `src/DSP/`, `src/DSP_AIDL/`, `runtime/asb_dsp_*.sh` |
| **Диагностика** | Проверка effective-state, support-отчёты, полевые записи и сравнение захватов. | `tools/asb_diag.sh`, `system/bin/asbdiag`, `tools/logkit/`, `tools/*report*.py` |
| **Regression и проверка поставки** | Native, shell, WebUI, исходное дерево и упаковка. | `tests/`, `tools/asb_full_regression.sh`, `tools/asb_source_regression.sh`, `tools/asb_tree_check.sh` |

Нативный governor является работающим policy-компонентом. Его нельзя путать с моделью диагностического сбора: постоянный governor не означает постоянный регистратор расширенных логов или worker инвентаря устройства.

## 4. Установка, обновление и удаление

### 4.1 Обычная установка

1. Установите обычный release ZIP через Magisk, KernelSU, APatch или поддерживаемую производную.
2. Перезагрузитесь, чтобы boot-mounts, нативные компоненты, аудиоинтеграция и сгенерированная политика устройства инициализировались в правильном порядке.
3. Откройте WebUI и выберите профиль.
4. Оставьте дополнительные настройки по умолчанию, пока не получите исходную картину работы.
5. Если выбранная настройка будто не действует, используйте **Action**, **Monitor** или `asbdiag`.

Не устанавливайте несколько пакетов ASB параллельно. Тестовая сборка заменяет существующий модуль обычным механизмом обновления менеджера.

### 4.2 Настройки и обучение — разное состояние

ASB разделяет пользовательскую конфигурацию, сведения об активном профиле, native learning, сгенерированные bounds устройства, baseline и диагностическое состояние. Это разделение важно:

- сброс конфигурации не должен незаметно означать удаление всех накопленных наблюдений;
- для обычной аудио- или сетевой настройки не требуется сбрасывать Smart learning;
- обновление может переносить совместимую конфигурацию и одновременно отклонять устаревшие доказательства устройства;
- сохранённая конфигурация не доказывает, что каждая опция поддерживается другим телефоном;
- выбор профиля не отменяет автоматически независимо включённые твики.

WebUI предоставляет именованные конфигурации, backup/export и отдельные действия сброса. Перед масштабным экспериментом создайте резервную копию, а к тестовой записи приложите сведения о прошивке и root-окружении.

### 4.3 Stock и удаление — не одна операция

**Stock** снимает активную профильную политику ASB и возвращает соответствующие решения производительности ROM. Это полезно для A/B-сравнения, но выбранный пользователем DSP, камера, сеть или интерфейс могут оставаться независимыми настройками.

**Удаление** запускает путь восстановления параметров, принадлежащих ASB. Baseline и записи владения позволяют не перезаписывать вслепую более новое постороннее изменение. После удаления перезагрузка является самым чистым способом вернуть mount- и boot-интегрированное поведение в стоковое окружение.

## 5. Профили и композиция политики

Профиль — это не один верхний предел CPU. В зависимости от открытых интерфейсов устройства и пользовательской конфигурации политика может включать диапазоны каждого CPU policy, GPU, scheduler uclamp, память/VM, температурную реакцию, фоновую работу и другие принадлежащие ASB настройки.

| Профиль | Назначение политики | Важная граница |
|:---|:---|:---|
| **Smart** | Выбирать и уточнять поведение по текущей нагрузке, истории сценариев, плавности, батарее и температурным доказательствам. | Обучение никогда не важнее термобезопасности, отклонения устаревших данных и владения платформы. |
| **Performance** | Сохранять высокую отзывчивость и запас для тяжёлой работы. | Не отключает термозащиту и не гарантирует аппаратный максимум в каждом состоянии. |
| **Balanced** | Обеспечивать предсказуемую ежедневную отзывчивость с умеренной экономией. | Это не просто Smart без обучения: диапазоны и поведение задаются отдельно. |
| **Battery** | Уменьшать лишние пики, предпочитать автономность и меньший нагрев. | Jank guard является ограниченной страховкой, а не вторым Smart learner. Тяжёлая работа может идти медленнее намеренно. |
| **Stock** | Возвращать ROM контроль над базовой политикой для сравнения или диагностики. | Не означает сброс каждой независимой дополнительной настройки. |

### 5.1 Потолок производительности

`perf_ceiling_pct` задаёт пользовательский верхний предел выбранной performance-политики. Это дополнительное ограничение, а не требование постоянно держать каждый кластер на указанном проценте.

Итоговое фактическое значение может быть ниже из-за:

- собственного state-dependent диапазона профиля;
- thermal budget или политики sustained;
- vendor clamp;
- отсутствующего или read-only интерфейса;
- OPP-таблицы, в которой нет точной запрошенной частоты;
- другого явного safety gate.

Когда значение необходимо привязать к реальной OPP-таблице, ASB использует консервативное правило потолка, а не округление вверх за пределы запрошенного cap.

### 5.2 Переключение профиля и переходное состояние

Переключение профиля может состоять из нескольких упорядоченных операций: остановка или передача native-политики, применение новых диапазонов, reconcile runtime-applier'ов, публикация состояния и проверка фактических значений. Диагностический снимок в этот интервал может быть переходным.

Если `asbdiag` показывает продолжающееся переключение, дождитесь завершения и повторите захват. Не делайте вывод о постоянном конфликте владельцев по одному промежуточному семплу.

## 6. Нативный governor

### 6.1 Шесть состояний

Governor использует конечный автомат. Состояние описывает текущую рабочую ситуацию и не является ещё одним пользовательским профилем.

| Состояние | Рабочий смысл | Общее направление политики |
|:---|:---|:---|
| `DEEP_IDLE` | Экран выключен в простое либо другая ситуация, прошедшая deep-idle gates. | Уменьшать ненужную производительность и фоновую стоимость, не принимая активный звук, навигацию, зарядку или VPN за сон. |
| `LIGHT_IDLE` | Слабая активность при включённом экране или лёгкая фоновая работа. | Сохранять базовый отклик без ненужного высокого уровня частот. |
| `MODERATE` | Обычная интерактивная работа, активность приложений или умеренная продолжительная нагрузка. | Давать полезный запас, не считая каждый всплеск игрой. |
| `HEAVY` | Значительная CPU/GPU-нагрузка, не выполняющая полный gaming-контракт. | Поднимать доступную производительность с сохранением thermal- и vendor-лимитов. |
| `SUSTAINED` | Длительная тяжёлая работа или температурное условие, требующее устойчивого уровня. | Менять короткие пики на стабильную производительность и контролируемый нагрев. |
| `GAMING` | Подсказка игры/приложения плюс подтверждающая нагрузка. | Приоритет интерактивной производительности; Battery может намеренно запрещать это состояние. |

Одного высокого GPU-показателя недостаточно для объявления игры. Подсказка игры без достаточной нагрузки тоже может привести лишь к heavy-состоянию, а не к безусловному максимуму.

### 6.2 Входные данные и взаимное подтверждение

Governor может объединять несколько классов метрик:

- частоты каждого CPU policy и сведения, связанные с utilisation;
- системную нагрузку и сигналы давления на ядра;
- активность GPU там, где платформа открывает осмысленный интерфейс;
- состояние экрана, касания/запуски и подсказки приложений;
- заряд, состояние зарядки и доказательства, связанные с расходом;
- thermal zones, признаки vendor clamp и метаданные уверенности датчиков;
- состояние камеры/медиа и другие scenario gates;
- нативные записи кадров/плавности и ограниченную обратную связь существующего log-пути.

Входные данные проверяются до арифметики или использования в политике. Отсутствующие счётчики, неправдоподобные дельты, устаревшие семплы и неподдерживаемые интерфейсы нельзя превращать в выдуманное значение нагрузки.

### 6.3 Гистерезис, dwell и эскалация

Мгновенная реакция на каждый семпл вызывала бы осцилляции и лишние записи. Поэтому вход, выход и удержание состояния используют разные механизмы:

- **dwell time** не даёт немедленно переключаться туда-сюда;
- **разные пороги входа и выхода** создают гистерезис;
- **corroboration** не позволяет одному слабому сигналу выбрать дорогое состояние;
- **pending-state logic** позволяет переходу подтвердиться более чем одним наблюдением;
- **thermal и emergency paths** могут обходить обычные performance-предпочтения, когда этого требует безопасность;
- **write suppression** не перезаписывает узел, если запрошенное значение не изменилось.

Поэтому фраза «нагрузка упала на один семпл» не означает обязательный немедленный выход из состояния. В то же время касание, запуск или правильно подтверждённая тяжёлая нагрузка могут оправдать более быструю эскалацию, чем обычное усреднение.

### 6.4 Продолжительная работа и холодные игры

`SUSTAINED` — не состояние сбоя. Его цель — найти уровень производительности, который устройство способно удерживать без постоянного попадания в сильную thermal-коррекцию.

`cool_gaming` и настройки sustained-temperature влияют на то, насколько рано ASB предпочитает такое устойчивое поведение. Они не отключают температурные датчики телефона и не гарантируют фиксированную температуру корпуса для всех игр, условий среды и прошивок.

`bat_suppress_gaming` не даёт профилю Battery входить в gaming-политику даже при обнаружении игры. Это намеренно: собственный performance-контракт Battery остаётся значимым.

### 6.5 Writer и сосуществование с vendor

Writer сравнивает запрошенное и наблюдаемое значения и фиксирует несовпадение вместо бесконечного цикла записи. Важные случаи:

| Наблюдение | Интерпретация и реакция |
|:---|:---|
| Наблюдаемое значение совпадает с запросом | Запрос сейчас эффективен; повторная запись не нужна. |
| Vendor удерживает более строгий ceiling | ASB не должен бороться с thermal или platform protection ради более высокого cap. |
| Vendor временно поднимает floor | Touch/launch/QoS boost не является автоматически ошибкой ASB или новым постоянным baseline. |
| Несовпадение повторяется | Backoff и capability handling уменьшают бессмысленные записи; диагностика показывает состояние. |
| Интерфейс отсутствует или read-only | Функция пропускается либо получает unavailable/not exposed; ложный успех не выводится. |
| Действует lease или handover | Другой определённый владелец временно управляет путём, исключая конкурирующие записи. |

Writer leases и явный handover являются инструментами владения, а не заявлением, что ASB всегда контролирует каждую частоту системы. Решения vendor thermal и PowerHAL остаются авторитетными там, где платформа их enforcing.

## 7. Device-adaptive CPU bounds

### 7.1 Зачем нужен синтез

Фиксированные частоты, скопированные с другого устройства, небезопасны и часто бессмысленны. ASB обнаруживает топологию CPU policy текущего устройства и аппаратные пределы, затем синтезирует диапазоны профилей из этих доказательств.

Discovery-путь read-only. Синтез записывает сгенерированные конфигурационные данные, а не новые аппаратные возможности. Если discovery не может надёжно установить идентичность, импорт должен fail closed, а не переиспользовать несовместимый файл.

### 7.2 Идентичность bounds schema 3

Schema 3 проверяет три взаимодополняющих части происхождения:

| Поле | Что подтверждает |
|:---|:---|
| `cluster_signature_full` | Полную сигнатуру физических policy/кластеров, включая те, которые не являются представителями little/mid/big. |
| `logical_roles` | Какая обнаруженная policy сейчас выполняет каждую логическую роль. |
| `policy_map` | Для каждой физической policy: числовой ID, native writer slot, аппаратный максимум и форму открытой OPP-таблицы. |

Это не даёт четвёртой policy, изменившейся роли, другой OPP-таблице или изменённому writer mapping пройти незамеченными только потому, что три основных кластера по-прежнему выглядят знакомо.

### 7.3 Формат `policy_map`

Каждая запись имеет вид:

```text
id:slot:hw_max:opp_count:opp_min:opp_max
```

Записи разделяются запятыми в каноническом порядке.

| Элемент | Значение |
|:---|:---|
| `id` | Числовой идентификатор `cpufreq/policyN`. |
| `slot` | Логический native writer slot; не обязательно совпадает с ID физической policy. |
| `hw_max` | Открытый аппаратный максимум этой физической policy. |
| `opp_count` | Число открытых OPP либо ноль, если пригодная таблица не открыта. |
| `opp_min` | Наименьшая открытая OPP либо ноль при отсутствии таблицы. |
| `opp_max` | Наибольшая открытая OPP либо ноль при отсутствии таблицы. |

Тройка OPP `0/0/0` является допустимой формой доказательства: **отсутствие `scaling_available_frequencies` автоматически не делает policy неподдерживаемой**. Аппаратные пределы и другие проверенные интерфейсы могут разрешать ограниченную работу, а отсутствие OPP-списка остаётся явно записанным.

### 7.4 Логические writer slots

| Топология | Slot 0 | Slot 1 | Slot 2 |
|:---|:---|:---|:---|
| **2-policy** | Little | Big | Не используется |
| **3-policy** | Little | Mid / big-class средняя policy | Prime |
| **4-policy** | Little | Mid / extra-class policy | Prime |

На 2-policy устройстве вторую физическую policy нельзя ошибочно называть `extra` только потому, что у парсера 3/4-policy есть такое поле. Физические ID и логические writer slots намеренно разделены.

### 7.5 OPP-aware синтез

Для каждого сгенерированного диапазона MIN/CAP/MAX ASB использует измеренный аппаратный предел policy и определённые профильные отношения или логику политики. При открытой OPP-таблице ceiling привязывается вниз к реальному элементу.

Если каждая открытая OPP выше запрошенной цели, наименьшая реальная OPP является единственным допустимым ненулевым ceiling. Округление до ближайшего элемента будет неправильным, когда оно идёт вверх, а независимое округление shell и native создаст разные политики.

Shell import и native import проверяют одну идентичность. Schema-2 или другой устаревший файл нельзя молча переосмысливать как schema 3.

## 8. Smart learning и evidence gates

### 8.1 Чему разрешено учиться Smart

Smart может накапливать scenario-specific доказательства из сопоставимых окон работы. Цель — ответить, улучшает ли дополнительный запас плавность, достаточен ли более низкий уровень или прежнее thermal/battery поведение делает кандидата нежелательным.

Smart не учится слепой записью нового значения после каждого скачка кадров. Кандидат проходит выбор сценария, freshness, validity, сравнение и cooldown до влияния на будущую политику.

### 8.2 Конвейер доказательств

| Этап | Назначение |
|:---|:---|
| **Выбор сценария** | Сравнивать наблюдения из достаточно похожих нагрузок и состояний устройства. |
| **Freshness check** | Отклонять данные, слишком старые для текущего окна. |
| **Deduplication** | Не считать повторную доставку одной подсказки независимым доказательством. |
| **Eligibility gates** | Исключать неподходящие условия зарядки, температуры, камеры, plateau или сценария. |
| **Bounded A/B window** | Сравнивать альтернативы ограниченное время, а не вносить бессрочное изменение. |
| **Native frame re-evaluation** | Повторно читать реальные graphics/smoothness данные и считать каждое окно один раз. |
| **Plateau handling** | Прекращать повторять сравнение, которое больше не даёт полезного различия. |
| **Cooldown и recheck** | Избегать немедленной осцилляции, но позволять позже перепроверить завершённый результат. |
| **Persisted learning** | Сохранять подтверждённые результаты отдельно от временных подсказок и пользовательской конфигурации. |

Завершённый plateau не является командой непрерывно проверять одну альтернативу. Freshness и recheck также не дают старому решению стать вечной непререкаемой истиной.

### 8.3 Log-assisted smoothness feedback

Существующий log-путь может передавать ограниченные jank-подсказки, которые назначают более раннее нативное smoothness-сравнение. Лог является входным каналом, а не владельцем политики:

1. подсказка должна быть свежей, ограниченной и дедуплицированной;
2. governor проверяет scenario, charging, thermal, cooldown и plateau gates;
3. native engine повторно читает реальные `GraphicsStats`;
4. каждое окно учитывается один раз;
5. менять политику может только обычный decision path governor.

Это разделение принципиально. Shell-парсер лога, напрямую записывающий CPU, обошёл бы native ownership и мог бороться с governor.

### 8.4 Проверенный parsing и ограниченный I/O

Числа feedback парсятся как проверенные 64-битные значения. Используется проверка в стиле `strtoull` с `ERANGE` и overflow checks **до арифметики**. Огромный счётчик нужно отклонить, а не завернуть переполнением в правдоподобную маленькую дельту.

Governor сохраняет обычный feedback gate и кэширует метаданные файла, чтобы не перечитывать неизменённое тело. Идентичность кэша включает:

- device ID;
- inode;
- размер файла;
- mtime с наносекундами;
- ctime с наносекундами.

Атомарная замена принципиальна: temp-file write с последующим `rename()` должен обнаруживаться как новое тело даже при совпадающей видимой длине. Прямая перезапись fixture не является эквивалентным тестом этого поведения.

| Счётчик | Значение |
|:---|:---|
| `smooth_log_checks` | Выполненные проверки eligibility/cache обратной связи. |
| `smooth_log_reads` | Сколько раз тело feedback действительно читалось. |
| `smooth_log_changes` | Наблюденные новые или изменённые тела feedback. |
| `smooth_log_unchanged` | Проверки, при которых кэшированное тело не изменилось. |

Эти счётчики поддерживают измерение стоимости. Сами по себе они не доказывают экономию батареи.

### 8.5 Батарея, зарядка и media gates

- `smart_battery_bias` добавляет явное пользовательское предпочтение экономии и не является learned temperature.
- `auto_battery_enable` управляет переключением при низком заряде и восстановлением прежнего профиля независимо от обычного scenario learning.
- `charge_aware_enable` разрешает больший запас на зарядке только при разрешении остальных gates.
- `smart_media_guard` не даёт принять media-oriented поведение за обычную интерактивную performance-проблему.
- Выключенный экран со звуком, навигацией, VPN или зарядкой может disqualify deep-idle выводы.

### 8.6 Prime-core escape

`heavy_prime_escape`, `prime_escape_burst_s` и `prime_escape_rest_s` предоставляют ограниченное prime-core облегчение для подходящих heavy-сценариев. Пара burst/rest выбрана намеренно: постоянный prime lift уничтожил бы смысл экономии и повысил нагрев.

Escape является временным ослаблением внутри остальных safety-ограничений, а не безусловным аппаратным максимумом или SoC-specific writer.

## 9. Температурные доказательства и защита

### 9.1 Разные температуры имеют разный смысл

Температуры CPU, junction, board, skin и батареи отвечают на разные вопросы. ASB может перекрёстно проверять доступные thermal zones и привязывать confidence к выбранному источнику. Производный или оспариваемый источник должен показываться с меньшей уверенностью, а не как равнозначно авторитетный.

Отсутствие skin/board zone может ограничить surface-политику даже при читаемой температуре CPU. Горячая батарея также не взаимозаменяема с показанием CPU die.

### 9.2 Adaptive thermal budget

Governor может снижать производительность до сильного platform clamp. Проактивный budget призван избегать неэффективной осцилляции «пик — троттлинг» и делать продолжительное поведение предсказуемее.

Budget не заменяет vendor thermal engine. Если платформа вводит более строгий предел, он побеждает. ASB не должен повторно поднимать ceiling против активного vendor clamp.

### 9.3 Пользовательские thermal-настройки

| Настройка | Роль | Осторожность |
|:---|:---|:---|
| `sustained_temp_mode` | Выбирает stock, Smart-managed или manual sustained-throttling поведение. | Manual меняет начало сдерживания ASB, но не сдвигает физические пределы аппаратуры. |
| `sustained_temp_enter` | Задаёт manual entry point для соответствующей политики. | Более высокое значение может означать нагрев и позднее сдерживание; низкое — более раннее снижение пиков. |
| `perf_ceiling_pct` | Добавляет общий performance ceiling. | Не является температурной целью и не гарантирует итоговую температуру. |
| `cool_gaming` | Смещает игры к устойчивому холодному поведению. | FPS зависит от игры и устройства; универсальный прирост не обещается. |
| `bat_suppress_gaming` | Не даёт Battery входить в gaming state. | Более низкая игровая производительность в Battery ожидаема. |

### 9.4 Thermal diagnostics

Полезный thermal-отчёт должен назвать источник, confidence, текущего владельца лимита и недавние vendor-доказательства. «ASB запросил большее значение» и «телефону сейчас разрешено его использовать» — разные утверждения.

Не считайте термозащиту сломанной только потому, что текущая частота ниже profile ceiling. Сначала проверьте `SUSTAINED`, thermal cap, vendor ownership, sensor confidence и переходное состояние переключения профиля.

| `dsp_outputs` | DSP Outputs | `all` | Выбирает speaker/wired/Bluetooth сочетания или отключает DSP с сохранением значений параметров. |
| `dsp_loudness` | DSP Loudness | `0` | Основной DSP enable/gain, 0–25 dB; первое включение effect может требовать reboot. |
| `dsp_bass` | DSP Bass Boost | `0` | Low-shelf boost; расходует headroom и приближает срабатывание limiter. |
| `dsp_voice` | DSP Voice Tone | `0` | Широкая настройка voice-body и presence-edge, особенно полезная маленьким динамикам. |
| `dsp_width` | DSP Stereo Width | `0` | Усиливает stereo side выше защищённой bass-области; mono/centre не расширяется так же. |
| `dsp_clarity` | DSP Clarity | `0` | Мягкий high-shelf до dynamics и финального limiting. |
| `dsp_rumble` | DSP Sub-bass Filter | `off` | Off/35/50/70 Hz high-pass; более высокие cutoff намеренно агрессивны. |
| `dsp_headroom` | DSP Output Headroom | `15` | Финальный sample-peak ceiling: соответствующие значения дают `-0.15`, `-0.30`, `-0.50` или `-1.00` dB. |
| `dsp_compressor` | DSP Compressor | `on` | Soft dynamics control для большого gain; финальный peak limiter остаётся и при выключенном compressor. |
| `audio_remove_volume_limit` | Headphone Volume Limit | `0` | Явный hearing-safety выбор; ASB не снимает эту системную защиту скрытно. |

#### DSP chain и смысл маршрутов

Порядок обработки имеет значение:

```text
sub-bass filter → bass → voice tone → clarity → stereo width
→ dynamics / compression → final sample-peak limiting
```

Gain, bass и width нельзя оценивать независимо от headroom. Большой bass boost перед limiter может уменьшить общую громкость, хотя его числовой уровень вырос. Headroom control является sample-peak ceiling, а не oversampled true-peak detector.

`dsp_outputs=off` убирает обработку ASB с выбранного пути без удаления tone- и dynamics-настроек. Выбор только фактического listening route не даёт применить speaker-oriented gain к наушникам или наоборот.

На встроенном громкоговорителе дополнительная thermal-политика может уменьшать DSP gain при горячей батарее и возвращать его после охлаждения. Wired и Bluetooth не управляются этим speaker-specific снижением таким же образом.

Bluetooth DSP может убрать воспроизведение с low-power offload path и удерживать CPU активным при выключенном экране. Поэтому battery-сравнение должно записывать выбранные DSP outputs, codec/offload state и audio route.

#### Внешние обработчики и effect interfaces

`eq_compat` подходит, когда ViPER, JamesDSP или другой внешний обработчик должен получить поток без ASB effect на том же processing path. Не диагностируйте два процессора как один effect.

Аудиоинтеграция ASB может использовать legacy effect interfaces и AOSP/AIDL компоненты. Это разные workflows:

- сборка native governor не пересобирает DSP;
- сборка AOSP/AIDL effect не доказывает локальную пересборку каждого поставленного DSP binary;
- reference/prebuilt DSP файлы нужно честно называть таковыми;
- ABI selection и attach evidence относятся к диагностике, а не выводятся из имени файла.

### 11.2 Запрошенное против фактического

Карточка конфигурации отвечает «что выбрал пользователь?». Сама по себе она не отвечает «что сейчас live?». Поэтому Monitor, Action и диагностика используют дополнительные доказательства:

- текущие sysfs/property/service значения;
- writer status и наблюдаемое несовпадение;
- активного vendor или lease owner;
- capability manifests и открытые интерфейсы;
- pending reboot/apply state;
- confidence и freshness metadata.

При отсутствии знаменателя нормализованная шкала должна скрываться, а не показывать произвольный процент. Unknown или warming-up остаются нейтральными. Reverse scales применяются там, где большее число автоматически не лучше — например, для доступного headroom в отличие от потреблённого ресурса.

### 11.3 Владелец лимита

«Кто задал лимит?» — диагностическая атрибуция, а не моральная оценка. Источником может быть ASB policy, shell/runtime policy, vendor/platform policy, thermal protection или unknown.

Vendor clamp может быть защитным и ожидаемым. ASB cap может намеренно следовать Battery или пользовательскому ceiling. Правильная реакция зависит от источника и текущего сценария, а не от обязательного удаления самого низкого видимого лимита.

### 11.4 Именованные конфигурации и backup

Именованные конфигурации полезны повторяемому тестированию, но не являются универсальными образами устройства. Перед импортом на другом hardware или firmware:

1. экспортируйте текущую known-good конфигурацию;
2. запишите модель, прошивку, ядро и root manager;
3. импортируйте без предположения, что неподдерживаемые значения применились;
4. проверьте capability и not-applied feedback;
5. при необходимости регенерируйте или проверьте device-specific bounds;
6. протестируйте каждую затронутую подсистему независимо.

## 12. Device information, приватность и качество доказательств

### 12.1 Read-only сбор по запросу

Device discovery читает публичные runtime-интерфейсы, необходимые для описания возможностей и совместимости. Ему не нужен постоянный inventory worker, и сбор фактов не должен изменять устройство.

Read-only сбор всё равно может дать неполный ответ. SELinux, конфигурация ядра, mount namespaces, отсутствующие узлы и firmware abstractions могут скрывать информацию от текущего процесса.

### 12.2 Данные, исключённые из отчётов

Диагностике ASB не нужно и нельзя читать:

- серийные номера устройства;
- IMEI или эквивалентные subscriber/device identifiers;
- имена аккаунтов или их содержимое;
- сетевые идентификаторы, например MAC-адреса или похожие уникальные link identifiers.

Пользователю всё равно следует просмотреть отчёт перед публикацией. Детали окружения, имена установленных пакетов или лично значимые filenames могут быть чувствительными в конкретном support-контексте, даже не будучи универсальными аппаратными идентификаторами.

### 12.3 Метки доказательств

При расширении диагностики используйте точные формулировки:

| Ситуация | Подходящий результат |
|:---|:---|
| Интерфейс отсутствует после определённого discovery | `not exposed` или `not runtime-discoverable` с контекстом. |
| Доказательства противоречивы или устарели | `unknown` / low confidence, а не удобная догадка. |
| Kernel config указывает на функцию | Только configuration evidence; не доказательство активного runtime-поведения. |
| Существует стандартный BPF/FUSE interface | Не доказывает специализированную функцию вроде FUSE-BPF. |
| Write request вернул успех | Запрос принят; по возможности ещё нужно проверить effective state. |
| Stock baseline нечитаем | Unknown baseline; нельзя выдумывать «stock» с другого устройства. |

Классификация происхождения ядра тоже indicative, а не provenance proof. Stock-like конфигурация не устанавливает, кто собрал ядро.

### 13.1 Повседневные команды


|:---|:---|

### 13.2 Полезные source-side инструменты

Исходный архив содержит отдельные инструменты discovery, effective policy, device verification, state audit, report generation и capture comparison. Их точные аргументы могут развиваться, поэтому читайте заголовок инструмента или `--help`, где оно реализовано, вместо предположения о стабильном scripting API.

### 13.3 Как читать сбой

Практический порядок:

1. **Воспроизведите** проблему и запишите точный сценарий.
2. **Проверьте profile state** и не идёт ли ещё переключение профиля.
3. **Сравните requested и effective** значения.
4. **Проверьте ownership**: vendor clamps, leases и другой applier.
5. **Проверьте capability evidence**, не превращая отсутствие доказательства в unsupported hardware.
6. **Проверьте pending reboot** для mount-, mixer- или boot-integrated изменений.
7. **Изучите логи с подходящей детализацией**, затем верните обычный log detail после теста.
8. **Выборочно вернитесь к Stock или defaults**, чтобы изолировать ответственную подсистему.

Не публикуйте secrets, credentials, приватные configuration files или личные идентификаторы вместе с support report.

## 14. Расширенные захваты и доказательное A/B-тестирование

### 14.1 Факты, гипотезы, рекомендации

Extended reports разделяют три слоя:

- **Факты:** sampled values, counters, transitions и наблюденные события.
- **Гипотезы:** правдоподобные объяснения, согласующиеся с этими фактами.
- **Рекомендации:** следующий эксперимент или mitigation, а не гарантированный результат.

Приложение рядом с событием расхода ещё не доказывает причинную связь. Wakelock может быть легитимной работой; restart процесса может быть следствием другого ограничения; radio может реагировать на плохой сигнал, а не на дефект приложения.

### 14.2 Построение сопоставимого захвата

Для осмысленного A/B-сравнения:

| Измерение | Необходимый контроль |
|:---|:---|
| **Состояние устройства** | Один телефон, firmware, kernel и root environment. |
| **Конфигурация** | Менять одну политику или чётко определённую группу; записывать остальные относящиеся настройки. |
| **Нагрузка** | Одно приложение, активность, длительность и максимально похожая пользовательская последовательность. |
| **Сеть** | Один route, сопоставимый сигнал, сервер и VPN state. |
| **Аудио** | Один output, codec/offload state, DSP route и громкость. |
| **Температура** | Сопоставимая начальная и окружающая температура; cooldown между прогонами. |
| **Батарея** | Сопоставимый начальный заряд, charging state и состояние батареи. |
| **Дисплей** | Сопоставимая яркость, refresh behaviour и screen-on time. |
| **Фон** | Исключить обновления, restore, backup и другую постороннюю тяжёлую активность. |
| **Длительность** | Достаточно репрезентативных idle и active фаз, а не только удачный короткий всплеск. |

Повторяйте прогоны. Показывайте разброс и аномалии, а не выбирайте самый красивый захват. Для screen-off drain сравниваемые окна должны иметь действительно похожую audio, navigation, VPN, charging и network активность.

### 14.3 Что нельзя заявлять

Нельзя выводить универсальный процент экономии батареи из одного before/after лога. Нельзя называть меньшую среднюю частоту доказательством эффективности, если работа завершилась медленнее. Нельзя называть больший benchmark throughput доказательством лучшего sustained UX без температуры и стабильности кадров.

Хороший результат называет свою область: устройство, прошивку, сценарий, конфигурацию, число семплов и неопределённость.

## 16. Сборка и regression validation

### 16.1 Source-only архив

Запустите полную source-only точку входа из корня репозитория:

```sh
bash tools/asb_source_regression.sh
```

Этот wrapper включает `ASB_DSP_REFERENCE_OPTIONAL=1` для full runner. Необязательными становятся только отсутствующие DSP reference prebuilts. Native governor checks, shell tests, WebUI tests, schema checks, runtime checks и warning policy остаются обязательными.

Source-only mode не является режимом «пропустить ошибки» и не заявляет пересборку DSP reference binaries.

### 16.2 Strict tree с DSP references

Для полного дерева, содержащего DSP reference prebuilts:

```sh
bash tools/asb_full_regression.sh
sh tools/asb_tree_check.sh check --strict
```

Full runner печатает validation mode и DSP-reference strictness. Native warnings проверяются по warning budget/baseline, чтобы новые предупреждения нельзя было незаметно скрыть.

### 16.3 Проверка чистого архива

Финальный архив нужно тестировать после восстановления в чистый каталог, а не только в working tree:

```sh
unzip -tq AutoSystemBoost-source.zip
unzip -q AutoSystemBoost-source.zip -d clean-tree
cd clean-tree/AutoSystemBoost-main
sh tools/asb_tree_check.sh check --strict
bash tools/asb_source_regression.sh
```

При создании source ZIP сохраняйте executable permissions. Проверяйте file set, hashes и executable modes против протестированного дерева. Успешный regression в другом каталоге не подтверждает архив с недостающими файлами.

### 16.4 Native и DSP workflows

У governor и DSP разные build requirements:

- governor build/test workflows используют native sources в `src/`;
- DSP legacy/AIDL components используют собственные sources и build integration;
- AOSP/AIDL builds отделены от обычной governor validation;
- нельзя называть reference DSP binaries локально пересобранными, если этого не было;
- нельзя ослаблять native warning checks ради прохождения поставки.

### 16.5 WebUI checks

WebUI validation должна охватывать реальные controls и видимые страницы, а не скрытые offscreen containers. Как минимум проверяйте:

- все пять профилей;
- dark, light и их Liquid Glass варианты;
- телефонные ширины 320, 360 и 412 CSS px;
- настоящие Config OFF/ON cards и switches;
- отсутствие horizontal overflow у видимого содержимого;
- отсутствие JavaScript runtime errors;
- settled computed styles после transitions, а не промежуточные animation frames.

Несуществующий selector или страница, которую не сделали видимой, может дать обманчиво зелёный harness. Тесты должны доказывать взаимодействие с нужным элементом.

## 17. Contribution и regression checklist

Перед отправкой behavioural change:

1. **Сформулируйте contract.** Что должно произойти, при каких доказательствах и что обязано остаться неизменным?
2. **Назовите owner.** Не добавляйте второй writer существующему native, vendor или shell-owned path.
3. **Сохраняйте profile identity.** Не превращайте Battery, Balanced и Performance в aliases Smart.
4. **Проверяйте весь ввод.** Range и overflow до арифметики; обрабатывайте stale и duplicate samples.
5. **Честно обрабатывайте missing evidence.** Unknown/not exposed вместо уверенных догадок.
6. **Избегайте universal device assumptions.** Не вводите SoC-specific writer или app-specific policy по одному capture без достаточных доказательств.
7. **Ограничивайте сбор.** Никакого нового persistent polling worker для device inventory или extended diagnostics.
8. **Защищайте приватность.** Никогда не добавляйте serial, IMEI, account или network-identifier collection.
9. **Тестируйте успех и отказ.** Supported, missing, read-only, vendor-limited, overflow и stale-identity cases.
10. **Тестируйте atomic state changes.** Если publication использует temp-write plus rename, проверяйте replacement, а не только direct overwrite.
11. **Запускайте full regression.** Focused tests полезны в разработке, но не заменяют финальную проверку.
12. **Проверяйте точный архив.** Strict manifest, clean extraction, hashes, executable modes и regression должны согласовываться.

Изменения документации тоже должны сохранять языковой паритет, рабочие перекрёстные ссылки, простой язык quick start и ясное разделение стабильной архитектуры и истории релизов.

## 18. Практические сценарии полевых тестов

Сфокусированный сценарий превращает смутное впечатление в проверяемый результат. Каждый тест ниже начинается с резервной копии known-good конфигурации и заканчивается восстановлением обычной детализации логов и временных экспериментальных настроек.

### 18.1 Smart и плавность

1. Выберите Smart и дайте устройству достаточно обычной работы для стабильной исходной базы.
2. Выберите один повторяемый интерактивный сценарий, например фиксированную прокрутку ленты или последовательность запуска приложения.
3. Запишите native state, сценарий, thermal condition, charge state и относящиеся feedback counters.
4. Если сценарий позволяет, создайте ограниченное jank-условие; не имитируйте обучение случайными записями настроек.
5. Проверьте, была ли подсказка свежей и eligible, запускалось ли native A/B window и перечитывались ли реальные frame evidence.
6. Повторно доставьте ту же подсказку для проверки deduplication и убедитесь, что одно окно не учтено несколько раз.
7. Отдельно проверьте атомарно заменённое и неизменённое feedback body; сравните counters checks, reads, changes и unchanged.
8. Попытайтесь начать новое сравнение в неподходящем thermal/charging/plateau условии и проверьте отказ, а не принудительный переход.

Критерий успеха — не «Smart всегда ускоряет». Правильным результатом может быть отсутствие изменения при недостаточных, повторных, устаревших или небезопасных доказательствах.

### 18.2 Топология и generated bounds

Проверяйте discovery/synthesis/import path на fixture с 2, 3 и 4 policy, а также на реальном устройстве. Контролируйте каждую физическую policy, а не только три привычные роли. Big-кластер 2-policy устройства обязан оставаться big, а не становиться `extra`.

Меняйте по одному элементу provenance: full cluster signature, logical role, physical policy ID, writer slot, hardware maximum, OPP count и OPP endpoints. Shell и native import должны отклонять устаревшую идентичность. Также проверьте отсутствующую OPP-таблицу в форме `0/0/0`; результат должен остаться явным, а не превращаться в автоматически неподдерживаемое hardware.

При синтезе проверяйте, что ceiling никогда не округляется выше запрошенной цели, а inverted или malformed ranges получают fail closed. Не используйте рабочий телефон как первое место проверки malformed fixtures.

### 18.3 Thermal и writer ownership

Начните при сопоставимой холодной температуре и создайте повторяемую sustained workload. Записывайте state transitions, requested ceilings, effective ceilings, thermal source/confidence и vendor-owner evidence.

Полезный тест включает три фазы: начальный ramp, продолжительную работу и cooldown. Проверьте, что `SUSTAINED` даёт стабильное поведение без непрерывной осцилляции, более строгий vendor clamp не вызывает борьбы, а обычная политика возвращается только при разрешении своих gates.

Если активен lease или vendor backoff, отсутствие повторной записи ASB не означает упавший governor. Захватите ownership state и дождитесь определённого handover/recheck path.

### 18.4 Батарея и ночное поведение

Сравнивайте эквивалентные screen-off окна с одинаковыми audio, navigation, VPN, charging и network условиями. Запишите начальный/конечный заряд, температуру и длительность, затем до изменения Doze или wakelock policy изучите deep-idle classification и wake activity.

Включайте по одному aggressive control. Проверяйте важные пользователю уведомления, fitness tracking, фоновое медиа, навигацию и Google-dependent функции. Меньший расход со сломанным необходимым поведением не является удачной универсальной рекомендацией.

Для Auto Battery пересеките low-charge условие, снова подключите зарядку и проверьте восстановление прежнего профиля без profile-switch loop. Для Charge-Aware повторите тест на тёплом устройстве, чтобы thermal gate по-прежнему побеждал.

### 18.5 DSP и аудиомаршруты

Тестируйте speaker, wired и Bluetooth независимо. Для каждого route записывайте `audio_profile`, `dsp_outputs`, loudness, tone settings, compressor/headroom, offload state и attach/ABI evidence.

Используйте один аудиоматериал и сопоставимую громкость системы/гарнитуры. Проверьте, что `dsp_outputs=off` убирает processing с сохранением параметров, а `eq_compat` оставляет поток внешнему процессору. First-enable reboot requirements проверяйте отдельно от live parameter updates.

Screen-off Bluetooth battery test нужно сравнивать с тем же Bluetooth route без ASB DSP. Иначе изменение offload/CPU wake behaviour можно ошибочно приписать наушникам, кодеку или музыкальному приложению.

### 18.6 Сеть и камера

Для сети выберите один route, отключите посторонние фоновые передачи и сравнивайте один сервер и workload. Подтвердите effective congestion control/qdisc на фактическом interface. Изменения сигнала и VPN использование записывайте как явные переменные, а не сноски.

Для camera grading перезагрузитесь при необходимости и снимите фиксированный набор сцен: дневная детализация, края портрета, macro texture, слабый свет и контрастные света. Ищите halos, banding и неестественный цвет наряду с желаемой резкостью. Camera performance hold проверяйте во время серий/видео, не смешивая качество изображения с отзывчивостью съёмки.

### 18.7 Обновление, Stock и удаление

Перед обновлением экспортируйте конфигурацию и запишите ожидания learning/state. Обновитесь обычным manager path, перезагрузитесь и проверьте migration совместимой конфигурации, generated-bounds identity и pending-reboot indicators.

Переключитесь в Stock и проверьте снятие profile policy без предположения, что независимые explicit tweaks сброшены. Наконец, проверьте uninstall restoration в контролируемом окружении: owned baselines должны восстановиться, mount-integrated поведение после reboot должно вернуться, а background diagnostic collector не должен остаться.

## 19. Диагностика по подсистемам

| Симптом | Первые проверки |
|:---|:---|
| Выбранный cap не равен live clock | Governor state, thermal cap, vendor owner, OPP snapping, active lease и завершение profile switch. |
| Smart не реагирует на один jank | Freshness, deduplication, scenario/charging/thermal gates, cooldown, plateau и native frame-window eligibility. |
| Battery кажется медленным в играх | `bat_suppress_gaming`, собственные ranges Battery, performance ceiling и thermal policy — это может быть intended behaviour. |
| DSP setting не даёт слышимого эффекта | `dsp_loudness`, выбранные `dsp_outputs`, текущий route, `audio_profile=eq_compat`, attach/ABI evidence и required reboot. |
| Bluetooth playback расходует больше с DSP | Выбранный Bluetooth DSP route и A2DP offload/CPU processing state. |
| Camera change сохранён, но не виден | Pending reboot, mount namespace, generated tone table и camera-HAL effective file. |
| Network option ничего не делает | Фактический route/interface, kernel algorithm/qdisc support, effective value и VPN state. |
| Уведомления приходят поздно | Doze level/exemptions, wakelock/GPS action, background trimming, GMS и process-limit settings. |
| Device page не показывает capability fact | Считать not exposed/not runtime-discoverable, пока нет более сильного read-only evidence. |
| Report нашёл только correlation | Оставить hypothesis; построить controlled repeat capture вместо обвинения. |

## 21. Финальная граница

ASB меняет поведение системы на устройстве с root. Ни одна adaptive policy не гарантирует одинаковые производительность, температуру или расход на всех устройствах и нагрузках.
